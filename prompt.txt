WHAT THE APP DOES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PaperLens is an AI research paper companion. Users upload any academic PDF. The app uses Gemini to:
1. Extract a visual interactive concept map (nodes + edges of key ideas)
2. Generate a Feynman-style ELI5 breakdown (section by section)
3. Auto-generate 10 exam-style questions with model answers
4. Let users chat with the paper via a context-aware Q&A interface

Firebase handles: Auth (Google Sign-In) and session history (Firestore only).
There is NO Firebase Storage. PDFs are sent directly to Gemini as base64 inline data.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
PDF HANDLING STRATEGY — CRITICAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Do NOT use Firebase Storage anywhere. Instead:

1. On the client, when user uploads a PDF, read it as base64 using FileReader:
   const base64 = await new Promise<string>((resolve, reject) => {
     const reader = new FileReader();
     reader.onload = () => resolve((reader.result as string).split(',')[1]);
     reader.onerror = reject;
     reader.readAsDataURL(file);
   });

2. Send the base64 string to the Next.js API routes via POST body as { base64, fileName, sessionId }.

3. In every API route, pass the PDF to Gemini as inline file data:
   {
     inlineData: {
       mimeType: "application/pdf",
       data: base64String
     }
   }

4. Store ONLY metadata and AI results in Firestore — never the PDF binary itself.

5. For the chat route, re-send the base64 PDF with every message request from the client
   (Gemini is stateless; the full context must be included each time).

6. Client-side validation: reject files where file.type !== 'application/pdf' or file.size > 10MB.
   Server-side re-validation in API routes: check Content-Type and base64 size before calling Gemini.
